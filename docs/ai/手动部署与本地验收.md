# 小电混合检索：手动部署与本地验收

本轮按用户补充要求在本地验收，生产主机由同事手动部署。本文的命令是交付操作步骤；不表示生产已部署或已通过验收。研究依据、原系统问题见《小电知识库诊断与迁移方案》，逐题验收见《小电验收场景》。

## 已实现的运行链路

电台 `/api/ai/chat` → 后端注入版本化小电系统提示词 → 模型输出结构化问题与追问改写 → 私有知识 API → BGE-M3 向量召回与中文 BM25 → RRF 合并 → BGE reranker → 正文与相邻段落 → 生成带实际证据 ID 的回答 → 客户端展示可打开的来源。

校园问答的历史仅交给问题理解模块；生成模块接收用户原问题、补全后的主题和当轮证据，不再次接收旧助手答案。原问题保留所有子问题，避免改写遗漏。这样资料被撤回后，旧答案不会绕过知识库状态过滤重新进入生成上下文。一般聊天和原文整理保留正常对话历史。

模型先输出答案，再在 `sourceIds` 中选择当轮简短编号（`S1`、`S2` 等）；后端校验并映射回真实段落版本 ID。前端只展示模型实际选择的来源，不把所有召回资料自动列为引用。

生成、问题理解和检索失败会直接报错，不转回旧词法检索或模板回答。原词法实现保留为 `retrieve_lexical`，用于离线基线比较。个人成绩、余额等没有接入真实工具结果的事项不能从 RAG 编造。

知识服务独立使用 SQLite 保存规范文档、段落、任务记录与追踪；Qdrant 保存向量。新索引完整建立后切换活动版本。重建期间查询仍用旧活动索引。新增、修改文档写入向量后发布规范文档，禁用/删除立即通过规范库过滤；帖子进入提示词之前另查业务库的公开状态、审核状态和内容版本。

HTML 先识别学校 CMS 正文边界；原文明确标注的发布日期才入库。图片式正文与扫描 PDF 走 OCR，Office 附件解析段落/表格。无法解析的资料进入失败报告。不能用导航、页脚、标题年份或抓取时间代替正文和发布日期。

## 本地运行

工作目录为仓库根目录。配置和测试会话都放在 Git 忽略的 `artifacts/ai/local/`，正式账号库不被测试修改。

```powershell
# 已有本地验收目录时直接复用，不重复创建。
ollama create xiaodian-local-instruct -f deploy/knowledge/Modelfile.local
python scripts/prepare_local_ai.py --source-db backend/data/treehole.db --student-id <获授权的学号> --output-dir artifacts/ai/local
powershell -File scripts/run_local_ai.ps1 -Service knowledge
powershell -File scripts/run_local_ai.ps1 -Service backend
```

本地 Qdrant REST 端口是 16333，知识服务 8091，电台 18080，Ollama 11434，均绑定 127.0.0.1。浏览器从 `http://127.0.0.1:18080/local-test-login.html` 进入隔离数据库的电台。该文件只是生成在本地构建目录中的验收夹具，不属于应用登录接口，禁止放入生产静态目录。

本地生成模型为 `qwen3:4b-instruct-2507-q4_K_M`，自定义模型名 `xiaodian-local-instruct`，保留模型原始模板，参数为 `num_ctx 8192`、`num_batch 128`、`temperature 0`。通过 `scripts/run_local_ai.ps1 -Service ollama` 启动时只为该进程设置单请求并行、Flash Attention 和 q8_0 KV cache。本机 8GB 显存同时运行 BGE 和生成模型，知识上下文预算设为 4096 字、最多选择 4 个命中后补相邻段。本地长历史/长原文仍受该模型窗口限制；生产应选择足够上下文窗口的模型并重新跑同一套验收集。

问题理解和答案生成均使用 OpenAI 兼容接口的 `response_format.type=json_schema`，供应商必须支持结构化输出；仅支持 JSON mode 的接口不能直接替换。问题规划固定字段与枚举；答案固定为 `answer` 和 `sourceIds`，引用 ID 只能取自当轮检索证据。接口不支持时直接暴露错误，部署时用实际供应商执行验收。校园问答与个人事务均检索公开知识，避免“个人数据”分类误判阻断公开办事资料。个人成绩、余额等实际记录仍需要独立授权工具，公共政策不能充当个人查询结果。

## 生产目录与配置

部署目标目录约定为 `/opt/zhixing-knowledge`，服务用户 `zhixing`。应用后端继续使用同事现有部署目录。知识库独立目录结构：

```text
/opt/zhixing-knowledge/
  current/knowledge_service/     Python 服务代码
  venv/                         Linux Python 3.11 环境
  knowledge.env                 私有配置，权限 600
  data/knowledge.db             规范知识库
  data/raw/                     原始资料快照
  models/bge-m3/                固定版本向量模型
  models/bge-reranker-base/      固定版本重排模型
  qdrant/qdrant                 Linux Qdrant 1.15.5
  qdrant/qdrant.yaml
  qdrant/storage/
  qdrant/snapshots/
```

使用 `deploy/knowledge/` 下的 systemd、Qdrant 配置及 env 模板。`KNOWLEDGE_API_KEY` 与应用的 `BACKEND_RAG_API_KEY` 必须一致。知识 API 和向量库只向本机开放；跨机器部署时使用现有受控内网并配置访问凭证。

独立推理环境必须支持 CUDA，或明确配置 CPU 并重新测量延迟；当前主机性能尚未核实，不能据此承诺吞吐量。Windows 虚拟环境和 Windows Qdrant 二进制不能复制到 Linux 运行。


## 导入、更新、切换与回滚

首次迁移时导入已验收的 `knowledge.db`，启动 Qdrant 与知识服务后，带私有 Bearer 凭证调用 `POST /reindex`。它生成新的活动索引版本；记录响应中的 collection、模型修订、维度、语料 hash 和片段数量。

日常新增官方资料通过 `python -m knowledge_service.refresh --urls <URL列表.json> --report <刷新报告.json>`；`KNOWLEDGE_URL` 和 API key 从受控环境注入。它调用运行中服务的 `/ingest`，完成正文解析与增量发布。`ingest.py`、`reparse.py` 直接操作 SQLite 的模式用于离线构建或停机维护，不要与在线索引发布同时执行。

`sources.json` 保存人工维护的官方入口。`discover.py` 从这些入口发现文章和服务地址。定期检查发现失败、采集失败、缺少日期、资料过时和验收缺口。学校域名可访问不等于文章正文完整；图片公告、附件和校内访问限制必须单独处理。

公开论坛资料用 `python -m knowledge_service.community --app-db <业务SQLite路径>` 同步，通过现有任务调度按分钟运行。只读取公开、审核通过且未删除的帖子；删除、改私密或修改正文后，业务后端即时过滤旧证据，后续同步更新索引。

附带 `zhixing-knowledge-refresh.*` 和 `zhixing-knowledge-community.*` 的 systemd service/timer 模板，分别按北京时间每日 03:00 刷新官方来源、上次同步完成一分钟后同步论坛。填写 `KNOWLEDGE_APP_DB`，赋予服务用户读取业务库的权限，完成首次索引后可由部署同事启用论坛同步。官方自动刷新暂不启用：当前采集发布会覆盖已有状态，尚需区分管理员禁用与解析失败，防止人工下架的资料被自动重新发布；本轮停止扩量，沿用固定知识快照。发现/刷新结果位于 `data/maintenance/`；这些 Linux 定时任务尚未在目标主机实跑。

发布前用 SQLite backup API 备份知识数据库，同时为当前 Qdrant collection 创建 snapshot，并保存模型修订、代码版本和配置。回滚必须恢复匹配的规范库、活动索引和模型版本，不能只切回代码。应用账户数据库不在知识库回滚范围内。

合并 `backend.env.fragment` 到应用私有配置，并更新后端代码与 Flutter Web/小程序客户端。Nginx 的 AI 请求代理超时需覆盖问题理解、检索、生成三阶段（当前客户端 165 秒，建议代理 180 秒）；这只是超时边界，实际响应延迟必须由验收报告衡量。

## 验收证据

每题记录用户问题、适用对象、原文日期、预期字段、实际回答、`traceId`、`promptVersion`、`systemPayloadHash`、索引版本、召回/重排/context/实际引用 ID。管理员可读取 `/api/admin/ai/traces/{traceId}`。判断依据是实际送往模型的提示词与证据，不只看前端显示的名字。

必须分别执行：普通问答、追问改写、长文本提取、跨段落材料与例外、时效冲突、缺资料、不相关问题、提示词注入、知识禁用、论坛删除/私密和两端来源跳转。`local-ui-acceptance.json` 只记录已亲自执行的界面场景，其余场景不会自动算通过。

目前生产域名不可用，生产上线、微信开发者工具/真机、目标主机吞吐量及持续运行验收均不能从本地结果推定通过。交付前需将实际测试报告中的未通过项逐项解决或明确列为未完成，不能用“商业级”标签替代这些证据。

## 手动交接包

在所有离线采集任务完成后执行：

```powershell
python scripts/package_ai_handoff.py --db artifacts/ai/knowledge.db --web artifacts/ai/local/web --models artifacts/ai/models --output artifacts/ai/handoff
```

输出三个包：`xiaodian-code-web.zip`（后端、知识服务、Web 构建与操作文档）、`xiaodian-official-data.zip`（SQLite 一致快照及官方原始 HTML/PDF 文件）、`xiaodian-bge-models.zip`（两套 BGE 权重和 tokenizer）。`HANDOFF.json` 给出整包 SHA256，每包内 `MANIFEST.json` 给出逐文件 SHA256。

规范库交接快照移除了社区帖子、问答追踪、采集任务日志和本机活动索引配置，并执行 VACUUM。接收端先解压数据包到 `/opt/zhixing-knowledge/`，将代码包内 `knowledge_service/` 放在 `current/` 下，模型包解压到根目录；首次启动后执行 `/reindex`。原始快照路径存为 `data/raw/...`，若需要离线重新解析，应从 `/opt/zhixing-knowledge` 执行并设置 `PYTHONPATH=current`。

Qdrant Linux 二进制、CUDA/Python 环境及生产生成模型配置需由同事按目标主机安装。Web 部分只复制 `web/` 到正式静态目录；本地登录夹具不在交接包中。小程序改动在仓库内，须通过原有微信发布流程构建发布。社区索引在目标主机首次同步时读取该主机业务库重新生成。
