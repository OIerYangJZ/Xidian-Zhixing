## 2. 已完成的改动（按提交顺序）

### 2.1 `51340f23` — 流式输出不再把读者拽回底部（对应问题 3）

**根因**：`AIChat.tsx` 的 `scrollIntoView` 依赖 `lastMessage.content.length`，**每个流式 delta 都触发一次**，且没有任何"用户是否主动上滑"的判断。

**改法**（`src/app/(protected)/ai/AIChat.tsx`）
- 给滚动容器加 ref 与 `onScroll`，阈值 `FOLLOW_THRESHOLD_PX = 80`
- 只有"用户本来就在底部"才跟随；上滑即释放，**流式继续但不滚动**；滚回底部自动恢复
- 新增「↓ 回到最新」悬浮按钮
- 发新问题时重新跟随

### 2.2 `2e760e58` — 失败原因不再伪装成"超时"（对应问题 4）

**根因**：`ai_timeout`（真超时）、`ai_budget_exceeded`（预算耗尽）、请求体被拒，原本渲染成**同一句**"请缩小问题范围"。

**改法**
- 新增 `src/lib/ai/errors.ts`，集中把错误码翻译成用户文案，三条路径共用
- 错误下方显示本轮消耗：`模型请求 N 次 · 工具调用 M 次 · 输入 X tokens · 输出 Y tokens`
- **顺带修掉一个隐藏故障**：`ChatRequest.history` 单条超 12,000 字符会让 FastAPI 返回 422，被前端误报成"DeepSeek 暂时无法完成请求"。现在返回 `ai_request_invalid` 并指出越界字段

> ⚠️ **（2026-10-09 记录）这次提交在 `agent_harness/app.py` 引入了 `from fastapi import ... Request`，覆盖了 `urllib.request.Request`，导致整个网页读取分支失效。已在 `7d922c58` 修复。** 教训：harness 里同时使用 urllib 与 FastAPI 时，`Request` 必须走别名。

### 2.3 `02ed81d8` — 跨轮上下文预算提高且不再丢整轮（对应问题 1）

**根因（两处）**
- 跨轮预算仅 24,000 字符、最近 16 条；超预算时**静默丢弃**最旧一轮
- 单条回复超上限会被**整条丢掉**，那一轮凭空消失

**改法**（`src/lib/ai/harnessHistory.ts` + `agent_harness/app.py`，两侧语义必须一致）

| 项 | 之前 | 现在 |
|---|---|---|
| 跨轮预算 | 24,000 字符 | **96,000** |
| 读取条数 | 16 | 40 |
| 单条上限 | 12,000 | 24,000 |
| 超长回复 | 整条丢弃 | **截断保留**，提问仍在 |
| 提问超预算 | 可能被截成半句 | **整条丢弃，绝不发半句提问** |
| 裁剪方向 | — | 从**最旧**一端丢（保留最近对话） |

**契约（其他 Agent 必须遵守）**：`ChatRequest.history` 与 `buildHarnessHistory()` 都按**最新在前**输入，返回**时间正序**；`message_history` 需要正序。

### 2.4 `9e1126ab` — 工具载荷加上限（对应问题 1 的"爆炸"）

**根因**：tool 结果会在**之后每一次请求里重发**，所以一次 `read_files(6×6000)` 或 `read_web_pages(5×8000)` 会主导整个回合。

**改法**：`READ_FILES_CHARS = 3_000`、`READ_WEB_PAGES_CHARS = 4_000`，并在工具描述里说明 `has_more` + `start` 可续读。

### 2.5 `a9e248e6` — 联网检索整批限时（对应问题 5）

**根因**：每个关键词各自 6–8 秒超时，8 组叠加 → 单次工具 16–22 秒，把回合推过 120 秒上限。

**改法**：整批共用一个 deadline，单个请求降到 6 秒。

### 2.6 `cfcda328` — 会话删除（对应问题 2）

**根因**：API 只有 GET/POST；`AiMessage→AiConversation` 与 `AiConversation→User` 都是 `onDelete: Restrict`。

**改法**
- 新增 `src/app/api/ai/conversations/[conversationId]/route.ts`
  - `DELETE`：**单事务内按 traces → messages → conversation 顺序删除**，校验 `userId` 归属
  - `PATCH`：重命名（长度 60，去空白）
- `AIChat.tsx` 会话 chip 加删除按钮 + 二次确认
- 新增 `tests/ai-conversation-admin.test.mjs`（4 条：顺序、越权、未登录、重命名校验）

### 2.7 `6774645c` — 小程序删除同步服务器（对应问题 2）

**根因**：小程序早有删除入口，但**只删微信本地缓存**，`backendId` 指向的服务器会话永远删不掉。

**改法**：`miniprogram2/api/ai.js` 新增 `deleteAiConversation()`；先删服务器，**失败则保留本地条目**以便重试。新增 `miniprogram2/tests/ai-conversation-delete.cjs`。

### 2.8 `5ba913ac` — 回合预算按实测值提高

**证据**：一次真实回合用了 11 次工具调用、累计 **184,442** input tokens，撞在旧的 180,000 上限上（而请求数只用了 9/12）。

**改法**：`input_tokens_limit` 180,000 → **600,000**；`per_request_input_tokens_limit` 50,000 → **150,000**（用户批准）。

### 2.9 `5442f86d` — 限制重复检索并引导读原文

**证据**：失败回合的工具序列是 `搜 → 搜 → 读 → 搜 → 找 → 搜 → 读 → 搜 → 搜 → 读 → 搜` —— **7 次检索、每次 8 秒、一次原文都没打开**。

**改法**
- `MAX_SEARCH_CALLS_PER_TURN = 5`，第 6 次直接 `ModelRetry` 拒绝，并在拒绝信息里指名改用 `read_files` / `read_web_pages`
- 工具描述与系统提示同步说明；有测试断言**"提示里写的次数必须等于工具真正执行的数字"**

### 2.10 `2fc1cd88` — 流式渲染按帧合批（问题 5 的前端部分）

**根因**：每个 `answer_delta` 都复制整棵会话树 + 用完整文本重新解析整篇 Markdown。

**改法**
- 新增 `src/lib/ai/streamBuffer.ts`：缓冲区 + **每帧最多写一次**；无帧时钟环境退化为 16ms 宏任务
- 流式期间渲染纯文本，`done` 后上 Markdown
- 新增 `tests/ai-stream-buffer.test.mjs`

### 2.11 `7d922c58` — 修复网页读取被遮蔽（**最重要的一个**）

**根因**：`agent_harness/app.py` 第 25 行 `from urllib.request import ... Request`，第 29 行 `from fastapi import ... Request` **把前者覆盖**，于是三处 `Request(url, headers={...})` 全部抛：

```
TypeError: Request.__init__() got an unexpected keyword argument 'headers'
```

影响面：`_fetch_campus_page`（读校方网页）、`_fetch_internet_page`（读互联网网页）、`_resolve_via_doh`（落地区域网关校验）**全部失效**。因为每个候选 URL 都要过 DNS 校验，`search_all_sources` 的互联网部分**永远返回 0 条**。

**这就是"检索永远超时"的真相：不是慢，是功能根本没通**，模型只能换词重搜直到预算耗尽。

**改法**：`from fastapi import ... Request as HttpRequest`（一行）。功能恢复后，另修三处设计问题：
1. **每个查询各自计时**，到点收走已有结果（原来一个慢引擎会让整批好结果一起被丢弃）
2. 去掉本机不可用的 backend（`mojeek` 超时、`startpage` 被 CAPTCHA 拦截），只留 `DDGS_BACKENDS = "duckduckgo,yahoo"`
3. 候选 URL 的网关校验改并发（原来串行 DNS）

**实测**：读校方网页 0.64 s / 3,992 字；联网检索 2 组关键词 2.72 s → **7 条真实结果**；8 组关键词 3.29 s → 7 条。

**为什么之前测试没抓到**：`setUp` 把 `_search_campus_pages` / `_search_internet_pages` 整个 mock 掉，网络层从未真正构造过一次请求。新测试**真的构造并调用**该路径。

### 2.12 `18288a27` — 答案三段式沉降（用户反馈的渲染问题）

**根因**：答案落地时连着两次突变、且落在同一帧 —— ① 纯文本 → Markdown；② Markdown → 加卡片。

**改法**
- 新增 `src/lib/ai/messagePhase.ts`：相位纯函数 `streaming` / `landed` / `final`
- `src/app/globals.css`：`.ai-answer` 字号过渡 + 两个关键帧
- 编排：**① 流式 0.94em → ② 200ms 放大回 1em + Markdown 淡入 → 停顿 120ms → ③ 卡片 fade-in 上移 4px**
- 时长通过 CSS 自定义属性注入并与 TS 常量同源
- 历史会话不带沉降窗口 → 打开旧对话不播动画
- **明确不做"思考过程"标注**（没有真实 reasoning token，标了即伪造）；卡片出现时正文**不压暗**

### 2.13 `e5ed7147` — 上游失败留下原因

**根因**：`ai_upstream_error` 不带 HTTP 状态与提供方原文，harness 日志只写 stdout（重启即丢），失败**事后无法定位**。

**改法**
- `_upstream_status()`：沿 `__cause__`/`__context__` 链取**最内层** HTTP 状态
- `_upstream_reason()`：取**最内层**提供方原文（`body` 优先），单行、≤500 字符
- 贯通到 SSE `error`、HTTP `detail`、harness 日志、trace 的 `metadata.failureReason`
- **harness 新增日志文件** `output/agent-harness.log`（滚动 2MB×4，`AGENT_HARNESS_LOG` 可覆盖），已 gitignore
- 新增 `scripts/diagnose_harness_turn.py` 诊断脚本
- 前端仍只显示面向用户的文案，提供方原文只落 trace 与日志

## 5. 阶段 3 方案：三档模式（`no-agent` / `pro` / `ultra`）

### 5.1 目标

把"这个问题值不值得跑 120 秒"交给用户决定，而不是由服务端猜意图。

### 5.2 三档语义（用户已确认）

|  | `no-agent` | **`pro`（默认）** | `ultra` |
|---|---|---|---|
| agent loop | **不走** | 走 | 走 |
| 工具 | 0 个 | `find_files` `search_docs` `read_files` `get_current_datetime` | 全部 |
| 联网检索 | 关 | **默认关** | 开 |
| 本地语料 | 一次预置检索（最多 8 篇摘要，不读原文） | 全量 | 全量 |
| 交互卡片 `present_ui` | 隐藏 | 隐藏 | 有 |
| `request_limit` | 1 | 8 | 12 |
| `tool_calls_limit` | 0 | 10 | 24 |
| 单请求 input 上限 | — | 60,000 | 150,000 |
| 回合累计 input 上限 | — | 240,000 | 600,000 |
| 单轮超时 | **30 s** | **75 s** | 120 s |
| 模型单次超时 | 25 s | 40 s | 45 s |
| 跨轮历史预算 | 48,000 字符 | 96,000 | 96,000 |
| 来源引用 | 有 | 有 | 有 |

**用户已定的两条产品决策**
1. **模式存在会话上**（`AiConversation.mode`），**切档时新开会话** —— 避免"ultra 的历史 + no-agent 的脑子"导致答案质量下降。
2. `no-agent` 下**本地检索未命中时**，回一句「**资料里没查到，要不要切 pro 查一下**」，**不让模型凭记忆硬答**。

**已定的技术结论**
- `no-agent` **不能用 `agent.run`**（必然带工具 schema）。正确路径是 `pydantic_ai.direct.model_request(model, messages, model_settings=...)`：一次请求，返回带 `.text` 与 usage 的 `ModelResponse`，完全不经过 agent loop。**注意**：它**不自动重试**，也**不会带上 agent 的 `instructions`**（系统提示要显式放进消息里）。
- 隐藏工具用 `prepare=` 钩子返回 `None`（`present_ui` 已在用这个机制，见 `agent_harness/app.py`）。
- 档位不靠重建 agent：`Agent` 无状态，`usage_limits` 与 `instructions` 都是**每请求参数**。

### 5.3 施工步骤（一小步一 commit，全部落在 `myfeature`）

| # | 任务 | 文件 | 拟用 commit |

## 6. 给其他 Agent 的操作约定

### 6.1 分支模型（用户明确要求，务必遵守）

- **常态只有两个分支**：`main` 与 `myfeature`。
- 日常改动**落在 `myfeature`** → PR 到 `main` → 用户合并后，把 `myfeature` 同步到最新（`git branch -f myfeature origin/main && git push origin myfeature`）。
- **只有大改动才开专用分支**（阶段 3 属于这一类）：在专用分支做完 → PR 到 `main` → 合并后把 `myfeature` 同步。
- **不要每个小功能开一个分支** —— 本次因为这样做，一度出现三个分支指向同一提交、`myfeature` 落后 main 一个阶段。

### 6.2 运行与调试

```powershell
# 启动 harness（Python 不热加载，改完必须重启）
.\.venv\Scripts\python.exe -m uvicorn agent_harness.app:app --host 127.0.0.1 --port 8002

# 健康检查
curl http://127.0.0.1:8002/health   # corpus_documents / model_configured

# 测一轮真实问答并看耗时/token/来源
#   需要 .env.local 提供密钥；脚本本身不打印凭据
.\.venv\Scripts\python.exe scripts\diagnose_harness_turn.py "物理学院有哪些科研团队"

# 排查线上失败：先看日志文件，再看 trace
Get-Content output\agent-harness.log -Tail 50
#   trace 里的 metadata.failureReason 保存了提供方原文
```

### 6.3 必须遵守的契约

1. **历史顺序**：`ChatRequest.history` 与 `buildHarnessHistory()` 都按**最新在前**输入，返回**时间正序**（`message_history` 需要正序）。
2. **Python 与 TypeScript 两侧的预算常量必须同步修改**（`agent_harness/app.py` ↔ `src/lib/ai/harnessHistory.ts`）。
3. **`Request` 必须用别名**：harness 内 `from fastapi import ... Request as HttpRequest`，`urllib.request.Request` 供页面抓取使用。
4. **系统提示里的数字必须等于工具真正执行的数字**（有测试断言）。
5. **测试不要 mock 掉被测函数本身**：联网检索的两个用例已移到独立测试类，不继承 `setUp` 的网络 mock，否则测的是 mock。
